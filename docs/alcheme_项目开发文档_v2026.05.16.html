数据库 4 张核心表
表名存什么核心字段
users用户账号id, email, created_at
notes每篇手记（用户输入 + AI提炼结果）
文字输入：raw_input存文字，voice_url为空
语音输入：raw_input存Whisper转写文字，voice_url存音频链接		id, user_id, raw_input, ai_distilled, second_voice, voice_url, whisper_used, created_at
note_summaries手记摘要，专门给 Agent 读，不是给用户看的id, note_id, summary_text, narrative_tags
letters每封来信，Agent 生成后存这里id, user_id, type, content, is_read, created_at
💡 note_summaries 是 Agent 的「原料库」。每次用户保存手记，后台自动生成一条简短摘要。Agent 每晚读摘要而非全文，大幅减少 token 消耗，降低成本。

四个文件夹的划分与调用关系
核心原则：变化原因不同的代码，放在不同文件夹。改一件事不影响另一件事。
文件夹负责什么改变原因跟谁说话
components/可复用的 UI 零件
动画、卡片、按钮		零件样式或行为要改被 screens 引用
screens/每个页面，只管显示什么
不管数据从哪来		设计改了、文案调了调用 hooks，引用 components
hooks/screens 和 api 的中间人
管理加载中/成功/失败状态		请求逻辑变了、需要复用被 screens 调用，调用 api
api/纯请求函数，跟 React 无关
只管发请求拿数据		接口地址变了、格式变了被 hooks 调用，连后端或 Supabase
例子：用户提交「说说」
screens用户点提交 → InputScreen 调用 useAlchemy.submit(text)，自己不管后续
hooksuseAlchemy 把 loading=true 告诉 screens（显示炼金动画）→ 调 api/ 发请求
apiPOST 到后端 /alchemy，等结果回来
hooks拿到结果 → loading=false，result=提炼内容 还给 screens
screens收到 result → NoteDetailScreen 用 components/NoteCard 把提炼结果渲染出来
AI Coding 开发流程
Step 0 · 准备工作

从 GitHub 克隆仓库到本地 → 装依赖（npm install）→ 本地跑起来（npm run dev）→ 浏览器打开能看到一个空白页或默认模板页，说明环境没问题，可以开始写代码了。（这一步的目的是验证环境配置正常，不是看产品页面。）

Step 1 · 确认 UI 和交互逻辑（接口契约出来后才开始）

在已有设计稿的基础上，整理每个页面的交互逻辑文档——不只是「点了跳哪里」，还要包括每个状态：比如倾诉页「输入框为空时按钮不可点」「提交中按钮显示 loading」「提交成功跳转炼金动画页」。

同时对照接口契约做交叉检查，验证接口的准确性：

· 页面需要显示的每个数据字段，接口都有返回吗？
· 字段名是否一致？（比如页面用 distilled，接口返回的是 ai_distilled？）
· 列表页需要的分页、排序字段有没有？
· 空状态、错误状态下接口返回什么？

Step 2 · 建组件库（在任何页面之前）

先建一个 theme.ts，把颜色、字体、间距的常量定义好，所有组件引用这个文件的变量，不要在组件里直接写颜色值。

然后把产品里反复用到的零件做出来放进 components/：按钮、输入框、卡片、图标、装饰图案、炼金动画、信封打开动效等。

跳过这步直接做页面，后期改一个颜色要改十几个文件。先建好，后面省很多时间。

Step 3 · 用 Mock 数据逐个页面开发

Mock 数据就是假数据——自己造一些假的手记内容、假的来信，写在 hooks/ 里，让页面看起来有内容，不需要等后端接口。两人并行开发，互不阻塞。

按页面优先级顺序开发（见下方）。每个页面做完，在 GitHub 开一个功能分支（如 feat/input-screen），推上去后 Vercel 自动生成预览链接，手机浏览器打开真实看效果——字体大小、间距、按钮大小在手机上和电脑上感受完全不同。确认没问题再合并到 main。

Mock 数据要写得像真的，用有意义的文字，不要用「test1 test2」。

Step 4 · 联调——替换成真实 API

后端接口做好后，联调由后端工程师主导，前端工程师配合。具体要做的事：

① 补全 api/ 文件夹——把真实的请求函数写进去。api/notes.ts 写真实的 Supabase 查询，api/alchemy.ts 写真实的后端请求地址（格式参照接口契约）。

② hooks/ 里替换假数据——把写死的 Mock 数据删掉，改成调用 api/ 里的函数。

③ 验证数据格式——后端返回的字段名和 Mock 数据里的字段名是否一致。最常见的问题：Mock 里叫 distilled，后端返回叫 ai_distilled，页面就显示不出来。接口契约定好就是为了减少这类问题。

Auth（用户登录）
Supabase 控制台开启，不需要自己写登录逻辑
配置 + 两种 key 的区别
控制台 → Authentication → Providers → 开启邮箱登录。同时开启 Row Level Security（行级权限）。

前端用 anon key（公开，配合行级权限只能读自己的数据）；后端两个 Service 用 service role key（管理员权限，能读所有用户数据，Agent 需要这个）。

交付标志：能用邮箱注册登录，登录后拿到 JWT token。

建一个叫 voices 的 bucket，存录音文件
工作流程
前端录音 → 发给 Service 1 → Service 1 存入 Storage → 得到唯一 URL → 存入 notes.voice_url → 前端用这个 URL 直接播放
supabase/ 文件夹（数据库版本管理）

放在项目根目录，与 app/ server/ 并列。后端工程师持续维护，不是一次性配置。

migrations/ — 每次改表结构，新建一个带日期的 .sql 文件（如 20260501_create_notes_table.sql），推到 GitHub，有记录可追溯。早期也可以直接在 Supabase 网站 SQL 编辑器手动执行。

seed.sql — 可选，初始测试数据，开发时用，不进生产环境。

目标：任何人克隆仓库，按顺序执行 migrations/ 里的文件，能还原出完整数据库结构。

Railway 配置 + 环境变量
配置步骤

1. Railway 网站建项目，连接 GitHub 仓库
2. 建 Service 1，根目录指向 server/service1/，Railway 读取其中的 railway.json 知道怎么启动
3. 建 Service 2，根目录指向 server/service2/，同上
4. 两个 Service 各自填写环境变量：CLAUDE_API_KEY、SUPABASE_URL、SUPABASE_SERVICE_ROLE_KEY
5. 之后每次推代码到 GitHub main 分支，Railway 自动拉取最新代码重启

冷启动问题：Railway 低配版长时间没请求会休眠，下次请求要等 5-10 秒才响应。解决办法：升级到不休眠的套餐（几美元/月），或用定时任务每 5 分钟 ping 一次保持活跃。

Key 名称放在哪为什么
Supabase URL前端 + Railway 两个 Service 环境变量各方都要连接 Supabase
Supabase anon key前端代码里（可以公开）专为前端设计的公开 Key，配合行级权限控制安全
Supabase service role key只在 Railway 环境变量管理员权限，绝不能暴露
Claude API Key只在 Railway 环境变量泄露会被盗用，费用全算头上
后端交付清单（按顺序）
步骤交付物验收标准

链路二：说说 → AI 提炼 → 保存手记 → 查看手记
1
前端 · Vercel
用户输入文字，点提交
携带 JWT，POST 到 Railway Service 1 的 /alchemy 接口。必须经过后端——Claude API Key 不能暴露在前端。
2
Railway Service 1 · middleware
JWT 验证 + 频率限制
auth.ts 验证 token 有效性，rateLimit.ts 防止 Claude API 被刷
3
Railway Service 1 → Claude API
AI 提炼
加载 prompts/alchemy.ts → 组合「用户输入 + prompt」→ 调 Claude API → 解析返回的 2-4 个提炼点（第一人称「我」开头）
4
Railway Service 1 → Supabase
同步生成手记摘要
summaryService 把这次倾诉的摘要写入 note_summaries 表，供 Agent 晚上读取。这一步对用户不可见。
5
前端 · Vercel
显示提炼结果
跳转炼金动画页 → 收到结果后展示 2-4 句「我……」。页面底部有轻柔邀请：「想不想用自己的声音，留住这几句话？」
6
前端 → Supabase · 直连
用户确认，保存手记
前端直接写入 Supabase notes 表（不经过后端）。原始输入 + AI 提炼结果 + 第二次叙述（如有）一起存，互不替换。
7
前端 → Supabase · 直连
查看手记本
前端直连 Supabase 读取 notes 表，展示手记列表和每篇详情（AI 提炼版 + 原始输入均可查看）。
链路二b：语音输入 → 转写 → 提炼（阶段二）
前端用户录音完成 → 音频文件 POST 到 Railway Service 1 的 /upload 接口（携带 JWT）
Service 1 → Whisper调 Whisper API 将音频转成文字（iOS 返回 m4a，Android 返回 webm，后端统一处理格式）
Service 1 → Claude转写文字走和文字输入完全相同的提炼链路（链路二 Step 3-4）
Service 1 → Storage音频文件存入 Supabase Storage voices bucket，拿到唯一 URL
Service 1 → 前端notes 表写入：raw_input（转写文字）+ voice_url（音频 URL）+ ai_distilled（提炼结果）→ 前端展示，用户可播放原始录音
链路三：Agent 自动生成来信 → 用户查看信箱
1
Railway Service 2 · 定时触发 · 零 token
每天凌晨 2 点自动启动
不需要用户在线。从 Supabase 读取「最近 30 天有手记」的活跃用户列表，逐个处理。
2
Service 2 → Supabase · 零 token
读取该用户的手记摘要
从 note_summaries 表读摘要（不读全文），控制 token 消耗
3
Service 2 → Claude API · 消耗 token
第一次调 Claude：判断要不要写信、写哪种
摘要 + prompts/trigger.ts → Claude 返回触发类型或「暂不触发」。暂不触发则跳过该用户。
4
Service 2 → Claude API · 消耗 token
第二次调 Claude：生成信件内容
摘要 + 对应类型的 prompts/letters/[类型].ts → 生成完整信件。这封信的质量由 prompt 决定，是产品魔法感的来源。
5
Service 2 → Supabase · 零 token
信件写入信箱，用户不知道
把信件写入 letters 表，is_read=false。用户下次打开 App，信箱悄悄有一封新信。
6
前端 → Supabase · 直连
用户打开信箱，查看来信
前端直连 Supabase 读取 letters 表，展示信件列表。点开某封信后标记 is_read=true，信封打开动效呈现。
七种来信 · 实现顺序
顺序类型触发逻辑核心感受
阶段一近期回顾手记积累到一定量「最近这段时间，你经历了这些」
阶段二随机回望随机抽一条旧手记「我今天突然想起你说过这句话」
阶段二深挖同一件事多条手记反复提同一件事「你知道你一直在想这件事吗」
阶段二模式发现多条手记背后指向同一特质「我看见了一条隐藏的线」
5悄悄变了叙事方式出现可见正向转变「你说话的方式和以前不一样了」
6久别来信用户很久没登录「你不在，但我一直记得你」
7 · 最后做年终回顾每年一次「看看时间在你身上留下了什么」
⚠️ 阶段一先实现「近期回顾」，跑通 Agent 基础链路。阶段二完成前四种来信。「悄悄变了」和「久别来信」触发门槛高，放后期。「年终回顾」最后做，需要足够长的用户数据积累才有意义。
