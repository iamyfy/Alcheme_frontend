本次重点
这一节只回答一件事：现在的口径是什么，团队要如何理解和配合。
这版文档仍然是给团队成员看的，不追求把技术细节讲到代码级，而是帮助大家看清楚： 现在的技术架构怎么理解； 前端、后端、Prompt 在每个环节各自要完成什么； 哪些内容给用户看，哪些内容只给团队内部用。
重点 01
“说说”主链路由后端统一收口
用户提交“说说”后，后端负责把 AI 提炼、手记保存、内部分析保存一起做完，再把完整结果返回前端。

这样做的好处是：减少前后不一致，前端也更容易联调。
重点 02
补充 profiles 资料层
Supabase 会自动维护登录账户，但产品自己的资料字段，比如是否完成引导、时区、最近活跃时间，仍然建议放在 `profiles` 表里。
重点 03
“给用户看的内容”和“系统内部内容”分开
用户看到的是手记、来信和基础资料。

内部分析、来信触发原因、夜间任务记录这些内容，只给后端和团队排查用，不直接给用户展示。
重点 04
触发原因保留，但放在内部记录层
团队需要知道“这封信为什么触发、参考了哪些手记”，这样后续调 Prompt 和调 Agent 会更顺。

但这些信息不直接放在用户可见的来信主表里，而是放在内部事件记录层。
整体项目结构
大方向仍然是前端 + 后端 + Supabase + Prompt 协作。
前端
React Web App，部署在 Vercel。
负责用户看到的一切页面、交互、动效、列表、详情和基础资料页。
后端
部署在 Railway，上面有两个 Service：
Service 1：接收前端请求，调用 AI，保存数据。
Service 2：每天夜里跑 Agent，判断是否要生成来信。
平台层
Supabase 负责数据库、登录、音频存储。
登录账户由 Supabase 自动维护；产品自己的资料层由 `profiles` 负责。
本版推荐理解方式
层主要职责
前端展示、交互、读取用户自己的资料、手记和来信
后端处理主链路、调用 AI、保存主数据和内部分析
SupabaseAuth、DB、Storage
Prompt定义提炼、内部分析、触发机制和来信内容
前端说明
前端工程师继续负责 React + TypeScript + Vercel。用户看到的一切都在这里。
前端最重要的理解是：前端负责提交、等待、展示、跳转；后端负责把“提炼 + 保存 + 内部分析”一起做完。
前端继续负责什么
继续负责首页、输入页、炼金页、手记本、手记详情、信箱、信件详情，以及用户资料相关页面。
前端不负责什么
前端不负责手记主记录落库，也不负责展示“来信为什么触发”这类内部调试信息。
后端说明
后端工程师继续负责 Supabase 平台层、Railway 代码层和 Prompt 协作层。
后端最重要的理解是：后端现在不只是给前端一个 AI 结果，而是真正承担主链路总控。
Service 1
负责在线请求：接收输入、校验身份、调用 DeepSeek、保存 `notes`、保存 `note_summaries`、返回结果。
Service 2
负责夜间 Agent：读取内部分析、判断是否触发来信、生成信件、写内部事件记录。
链路全览
把产品里最重要的几条链路重新讲清楚。
链路一：注册 / 登录
用户注册和登录，仍然由 Supabase Auth 负责；登录后进入产品。
链路二：说说 → AI 提炼 → 保存手记 → 查看手记
1. 用户在前端输入内容并提交
2. 前端把内容交给后端
3. 后端调用 DeepSeek 做提炼和内部分析
4. 后端保存手记和内部分析
5. 后端把结果返回前端
6. 前端展示提炼结果并进入手记详情页
链路三：语音输入
前端录音后，把音频交给后端。后端负责转写、提炼、保存，前端负责展示。
链路四：Agent 自动生成来信
Agent 夜间读取内部分析，判断是否触发来信，生成后写入信箱。

用户看到的是信件正文；团队内部会另外保留触发原因和参考依据，方便后续排查和优化。
团队分工
按角色看清楚每个人现在该完成什么。
产品 + 后端
负责数据库、接口、后端主链路、Agent 框架，以及交付“表结构与接口契约”。
1. 敲定表结构：哪些表、每张表存什么、谁能看、谁能写。
2. 敲定接口契约：前端提交什么、后端返回什么、字段怎么命名。
3. 保证主链路由后端统一收口。
4. 给 Agent 保留内部调试记录。
前端工程师
负责所有页面、动效、展示和接口联调。
1. 按新的接口契约接后端。
2. 继续推进页面、交互和动效。
3. 读取用户自己的资料、手记和来信。
Prompt 工程师
负责“说说”提炼、内部分析、触发机制和来信内容。
1. 打磨“说说”提炼 Prompt。
2. 定义 `analysis` 的内部结构。
3. 负责来信触发和来信内容的 Prompt 质量。
